# F03 — Extension registry handoff

Implemented and checked **2026-11-03**, using the F01 graph and F02 scientific
contracts. Four independently registered generic extensions exercise a moving
point, arithmetic operator, geometry factory and view adapter. No astronomy
package is required. The next task is **F04 computation runtime**.

## Public interfaces

`src/registry/index.js` exports `ExtensionRegistry`, `runContractTests`,
`prepareManifest`, `resolvePorts`, `matchesVersion`, `validateSchema`,
`validateData`, `applyDefaults`, and the API/manifest/schema/registry limits.
The complete developer guide is [extension-registry.md](../extension-registry.md).

```js
const registry = new ExtensionRegistry({ capabilities: ['dataflow.sync'] });
registry.register({ manifest, implementation, referenceCases });
const binding = registry.bind();
const project = new Project({ validators: binding.validators });
const draft = project.begin();
const author = binding.author(draft);
const point = author.instantiate('example.point', { parameters: {} });
draft.accept();
const result = binding.evaluate(project, point.id, {
  port: 'position', time: { value: 2, unit: 's' },
});
```

| Interface | Contract |
| --- | --- |
| `register(record)` | Validate and register trusted installed callbacks atomically; returns the registry. Dependencies must already be registered. |
| `discover({kind?})` | Detached data containing API version, host capabilities, limits, diagnostic codes, manifests, declared review status, reference-case summaries and latest test reports. |
| `inspectRequirements(graph)` | Read-only `{valid,requirements,errors}`, including missing/version-incompatible extensions and compatible installed transitive dependencies. Never loads code. |
| `bind({limits?})` | Frozen snapshot of installed records/capabilities; optional F02 evaluation limits. Later registrations require a new binding. |
| `binding.validators` | F01 structural hooks enforcing registry, F02 scientific, and visual contracts for acceptance, load and history restoration. |
| `binding.author(draft)` | Existing F02 author methods plus `instantiate(id,{id?,parameters?,inputs?,assets?})`, returning real F01 handles. |
| `binding.inspect(graph)` / `requirements(graph)` | Full acceptance checks / extension requirement inspection. |
| `binding.evaluate(project,id,request)` | Checked F02 scientific result envelope, preserving implementation build and project identity. |
| `binding.produce(project,id,{time?})` | Checked declarative artifact result with identity, producer, validity, artifact and diagnostics. |
| `runContractTests(id)` | Execute data-only cases through real acceptance/evaluation; retain report separately from review declarations. Also exported as `runContractTests(registry,id)`. |

`binding.flow` exposes the underlying F02 facade for existing calculations. Use
the binding's validators/evaluate/produce for registry-backed projects. F02 gained
`flow.describe(graph) -> {valid,errors,outputs}` to expose its resolved port
descriptors, and permits optional `node.data.extension` on injected models.
Registry validation owns that pin; no parallel graph, units or port system exists.

## Manifest, instance and callback contracts

Manifest `schemaVersion` and `apiVersion` are both **1**. Common fields are:

```js
{
  schemaVersion: 1, apiVersion: 1,
  id: 'example.point', version: '1.0.0',
  implementation: { id: 'example.point-implementation', version: '1.0.0', build: 'build-1' },
  kind: 'model', // or operator, asset-factory, view-adapter
  parameters: objectSchema,
  ports: { inputs: {}, outputs: { position: scientificPortDescriptor } },
  dependencies: [], // {id, version, build?}
  capabilities: ['dataflow.sync'],
  documentation: { summary: '...', links: [], examples: [{ parameters: {} }] },
  diagnostics: [{ code: 'OUTSIDE_MODEL', description: '...' }],
  science: { /* scientific kinds only; see below */ },
}
```

Scientific manifests require equations, references (`{title,locator}`), assumptions,
applicability declarations (`{id,description}`), evaluation behavior and review.
Evaluation currently permits `mode:'analytic'|'stateless'` and sampling entries
`'instant'|'stored-series'`. Every declared applicability guard must have exactly
one installed function. Review is `{status:'experimental'|'reviewed',notes,evidence}`;
declaring reviewed requires nonempty evidence, but does not verify it.

Visual manifests have empty scientific outputs and declare
`artifact:{kind,format,schema,provenance:{source,license}}`. Artifact kinds are
geometry, material, data and view. Optional `assets` maps slots to `{kind,format}`.
The artifact schema validates the returned **data**, not an artifact wrapper.

Parameter/artifact schemas use a bounded subset: object, array, number, integer,
string, boolean and null (integers must be safe integers); closed object
properties/required fields; array items
and length bounds; numeric bounds; scalar enum; defaults and descriptions.
Open property maps, references, expressions and arbitrary schema execution are
unsupported. Defaults fill missing properties only; validation rejects invalid
values. `instantiate` applies defaults; loading does not silently repair data.

Ports reuse exact F02 descriptors. Literal templates `{$param:'topLevelName'}`
and `{$node:'id'}` allow parameters and instance identity to specialize descriptors.
There is no expression language or nested path lookup. Static declarations are
checked at registration; resolved ports are checked before accepting an instance.
Documentation examples must validate after defaults are applied.

Instances use F01 kinds: model → component, operator → calculation, visual →
presentation. Their type is the extension ID and their data is exactly:

```js
{
  parameters: { /* schema-checked data */ },
  inputs: { slot: { port: 'outputName' } },
  extension: { id, version, implementation: { id, version, build } },
}
```

F01 `references['input.'+slot]` and `references['asset.'+slot]` identify targets;
`dependsOn` contains their distinct IDs. Acceptance checks exact correspondence,
scientific-port compatibility and artifact kind/format. Ordinary unpinned F01
relationships remain allowed, including relationship cycles. Computational cycles
still reject. F02 built-ins cannot carry extension pins. Other unavailable types
remain identifiable requirements and prevent acceptance/evaluation.

Scientific implementation callbacks are
`evaluate({node,inputs,request}) -> {port: Value}`. Visual callbacks are
`create({node,inputs,assets,request}) -> artifactData`, where assets contain full
checked artifact envelopes. Optional `validate(node)` and scientific
`guards:{guardId(node)}` return diagnostics. Inputs are detached and frozen;
callbacks are synchronous. Promises fail with `ASYNC_IMPLEMENTATION`.

`produce` evaluates scientific inputs at one requested physical time, preserves
their diagnostics, recursively memoizes artifact dependencies, validates output
data, and enforces an aggregate artifact budget. Results are
`{identity,producer:{nodeId,implementation},valid,artifact,diagnostics}` with
`artifact:{kind,format,data,provenance}` or null on failure. Results cannot succeed
after project changes during validation, evaluation or production; stale completed
outputs report `STALE_RESULT`, while other failures may report their own error
first. Consumers must still compare the identity triple after later edits/loads.

## Trust, review and version rules

The composition root imports selected installed modules and calls `register`.
Learners instantiate/connect/edit installed blocks; model development is a
separate trusted local-code workflow. Saved pins and source-looking text cannot
register code, resolve filesystem imports, fetch packages or execute equations.
External author scripts remain ordinary programs in the author's own process.

This is not a sandbox: trusted callbacks can use closures, consume CPU or perform
side effects. Immutable arguments and work limits do not preempt arbitrary code.
Host capabilities are explicit declarations, not permissions or feature probes.
Build identities and provenance/licenses are declared metadata, not verified
content hashes or rights checks.

Extension and implementation versions must be exact `N.N.N` releases; ranges and
prereleases are unsupported. Namespaced IDs cannot use the reserved `dataflow.`
prefix. Each registry holds one record per extension ID: duplicates reject, with
no overwrite, unregister or hot reload. Separate registries can hold other builds.
Dependencies require exact extension versions and optionally exact build strings;
all required host capabilities must exist at registration. Saved instances pin
the full extension and implementation identity/build, and incompatible reopening
fails without changing accepted state.

Discovery reports `independentlyVerified:false` even for a declared reviewed model.
Reference-test reports always contain `scientificCertification:false`; passing
cases never changes a declaration or certifies scientific accuracy. Empty suites
do not pass. There is no universal conservation-law requirement.

## Reference cases, checks and limits

Cases carry unique report labels, descriptions, parameters, scientific inputs,
optional asset instances, a request, and either expected outputs/artifact data or
one expected error code. Numerical acceptance uses
`abs(actual-expected) <= absolute + relative*abs(expected)`, with finite
nonnegative tolerances (default zero). Values also require matching F02 context;
expected warnings and approximation statements must survive. Artifact comparisons
check shape/keys and data. Each case uses a fresh validated F01 Project, constant
inputs and installed asset instances. Cases cannot submit executable test code.

Executed with bundled **Node 24.22.1**:

- `bash scripts/node.sh --test`: **167 tests passed**, zero failures/skips;
  all 121 earlier tests plus 13 manifest/schema and 33 registry integration tests.
- `bash scripts/node.sh examples/extension-registry.mjs`: four extensions and
  **8 passing reference cases**, including two expected applicability failures.
  At 2 seconds the point is `[5,-4,4]` m; signed scaling yields `-7.5` m.
  Changing marker scale preserves the scientific position.
- Tests exercise malformed manifests, duplicate IDs, unsupported versions,
  missing dependencies/capabilities, unavailable builds, transitive requirements,
  incompatible ports/assets, actual output validation, stale scientific/visual
  results, async rejection, artifact budgets, immutable inputs, false reference
  expectations, and inert executable-looking saved text.
- An isolated subprocess copies only core/dataflow/registry and a local fixture;
  all four extension kinds work without astronomy files. Recursive import-boundary
  checks pass. Shared modules contain no domain-name dispatch.
- Syntax checks and `git diff --check` pass. Approved logo bytes, BSD-3-Clause
  license, dependencies and existing astronomy/runtime/UI files are unchanged.
  No UI changes or browser review are part of F03.

Default registry limits are 64 extensions, 64 cases per extension and 10,000
aggregate artifact entries/string characters per production. Schema limits are
depth 24 / 1,024 schema nodes and depth 64 / 100,000 data nodes. F02 graph/value/work
limits remain in force; `discover` reports their defaults, while a binding may
explicitly override F02 limits. These are deterministic contract/work bounds, not
a wall-clock or total process-memory guarantee.

Unavailable manifests cannot reveal their unknown transitive dependencies.
Artifact production has no renderer, external asset resolver, disposal lifecycle
or content hashing. There is no stateful/async runtime, portable archive, command
gateway or agent session yet. The old v0.2 application remains separate.

## What F04–F09 must consume

- **F04:** extend this registry's declared capabilities and callbacks with actual
  analytic/stateful lifecycles, scheduling, cancellation and checkpoint identity.
  Preserve F02 Values, time coordinates, warnings and F01 identity; introduce no
  alternate graph or extension registry. Current callbacks cannot be preempted.
- **F05:** consume registered visual artifacts and checked scientific results,
  adding scene handles, explicit mappings, browser rendering, content identities
  and resource disposal. A view artifact here is data, not rendered pixels.
- **F06:** discover registered view capabilities for the shell and inspectors;
  surface units, model assumptions, provenance, availability and declared review
  honestly. Keep cameras and display controls independent of scientific values.
- **F07:** derive command schemas/defaults/examples/capabilities from discovery;
  route authoring through binding validators and F01 transactions. Add gateway
  context/idempotency/revocation without making a second acceptance authority.
- **F08:** conversation composes installed blocks through F07. Runtime filesystem
  access is a separate boundary; project text never becomes an installed model.
  Discovery/test reports must not be presented as independent scientific review.
- **F09:** preserve pins and source/provenance as data; inspect requirements before
  replacing accepted work, and report unavailable builds explicitly. Do not
  auto-install modules or execute author recipes on reopen. Extend persistence
  with F04 checkpoint state and F05 assets rather than treating this graph-only
  round trip as a complete project archive.
