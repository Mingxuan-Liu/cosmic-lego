## Concrete interfaces

Import from `src/core/index.js`:

```js
import { Project, createProject, validateProject, KernelError } from './src/core/index.js';
```

- `createProject({id?,title?})` creates empty graph data.
- `new Project({id?,title?,validators?})` creates accepted state, initially revision
  zero. `Project.from(data,{validators?})` validates existing data in a fresh runtime.
- `project.snapshot()`, `.get(id)`, `.token`, `.history`, and `.dependencies(id,options)`
  inspect accepted state. Returned graph/node data is detached; accepted handles
  are read-only, retain their IDs across revisions, and resolve current content.
- `project.begin(token = project.token)` returns a staged draft. It supports
  `create`, `component`, `calculation`, `presentation`, `connect`, `get`, `update`,
  `disconnect`, `remove`, `dependencies`, `snapshot`, `validate`, `preview`, and
  `accept`. Draft handles expose `id`, `value`, `set`, `connect`, `remove`, and
  `dependencies`. Author loops and helper functions execute in the author's process.
- `project.apply(operations,token)` atomically validates/accepts raw data commands.
  The five commands are `create`, `update`, `connect`, `disconnect`, and `remove`.
  Their exact payloads and handle signatures are in
  [the public guide](../composition-kernel.md).
- `project.preview(operations,token)` and `draft.preview()` return
  `{project,validation,baseToken}` without committing. Previews do not reserve a
  revision; acceptance reruns validation. Explicit IDs make raw preview/apply
  pairs retain creation IDs. Draft preview/accept retains automatically generated IDs.
- `project.accept(draft)`, `undo(token)`, `redo(token)`, and `load(data,token)` return
  detached accepted graph data. Read `.token` for the new mutation identity.

The serializable graph is:

```js
{
  schemaVersion: 1,
  id: 'project-id',
  title: 'A generic construction',
  nodes: [{
    id: 'node-id',
    kind: 'component', // or relationship, calculation, presentation
    type: 'extension.type',
    data: {},
    references: { slot: 'another-node-id' },
    dependsOn: [],
  }],
}
```

Node IDs are globally unique within one project. Kind, type, and ID cannot be
patched. Updates replace each supplied `data`, `references`, or `dependsOn` field
in full. `data` is a plain finite JSON object, with a 100-level nesting limit;
functions, accessors, undefined values, class instances, sparse arrays and cyclic
JavaScript data are rejected. Strings that resemble scripts or module paths are
inert. Project data does not select an implementation, import modules, or execute.

Relationships are first-class typed nodes with `references.source` and
`references.target`. Additional named references are allowed. Components,
relationships, calculation definitions and presentation definitions share the
same identity/reference machinery. Calculation/presentation definitions have no
evaluator or renderer in F01.

## Identity and revisions

Tokens contain **all three** fields `{projectId,generation,revision}`:

- Project identity belongs to authored content and survives an ordinary round trip.
- Generation is a fresh UUID-based runtime/load identity. Constructors,
  `Project.from`, and every successful `load` issue a fresh one.
- Revision starts at zero and strictly increases on acceptance, undo, redo and
  load within a runtime. Undo restores content, never an old token.

All raw mutations and raw preview require an explicit complete current token.
Draft creation captures a token; draft acceptance checks it. Foreign or stale
drafts cannot overwrite accepted state. A successful load advances revision,
changes generation, clears history, and invalidates previously issued handles,
drafts and commands even when it loads the same project or older content.
An independent `Project.from` may start at revision zero; its different generation
still invalidates old commands. Tokens are concurrency identities, not permissions
or authentication credentials.

Undo/redo revalidates the restored candidate and restores exact node IDs and
references. A successful new edit after undo discards redo; previews and failed
edits preserve it. Accepting an unchanged draft is still a new edit. Load history
does not span projects. Edit history is not an authored animation timeline and is
not serialized into graph data.

Draft handles remain tied to their draft after acceptance; the draft closes to
further edits. Reacquire a live accepted handle with `project.get(id)` or a writable
handle from a new draft. Accepted handles identify the current record with that
ID; they fail while it is absent and resolve it again if undo or deliberate ID
reuse brings it back. All handles from a previous load remain stale.

## Drafts, authoritative acceptance, and deletion

Draft operations check local shape/IDs, supported fields and finite data, but allow
missing reference targets, required relationships and type-specific data. A label
can be authored before its point/anchor. Acceptance checks the whole completed
graph. A failed local operation leaves the draft untouched; a failed acceptance
leaves accepted content, token and history untouched and permits draft repair.

Graph validation checks schema, unique IDs, all reference and dependency targets,
and computational cycles before invoking extension hooks. Ordinary reference
and relationship cycles are allowed. Computational dependencies must be acyclic
until a reviewed coupled-model facility exists; `DEPENDENCY_CYCLE` identifies
nodes blocked by a cycle, which can include downstream consumers.

Queries accept `{direction:'incoming'|'outgoing',edge:'reference'|'computation'|'all',
transitive:boolean}`; defaults are outgoing/all/false. Results are sorted, distinct
IDs excluding the start. Reference edges run from the owning node to its targets,
so a relationship points to both endpoints; they are not implicit endpoint-to-
endpoint computational edges. Iterative visited-set traversal terminates on cycles.
Draft queries may expose missing target IDs before acceptance.

Removal rejects incoming references/computational consumers unless `cascade:true`
is explicit. Cascade removes the target and its incoming transitive dependents,
including incident relationships. It does not indiscriminately remove referenced
endpoints. `disconnect` removes only a relationship and also rejects its own
referenced removal. Cascade cannot infer constraints hidden in arbitrary hooks:
the resulting graph still must validate. The example explicitly records
`label.references.anchor` so a point cascade can find its label through the anchor.
Another tested fixture omits that edge and requires an additional explicit label
removal in the same atomic batch.

## Extension validation boundary

The composition root injects:

```js
{
  structure: [project => [{code, path, message}]],
  types: { 'extension.type': (node, {project, get}) => [{code, path, message}] },
}
```

An empty diagnostic array means success; `get(id)` returns the immutable node or
undefined. Hooks must be trusted, pure synchronous functions. Their configuration
is copied at construction, and their candidate inputs are detached and deeply
frozen. Exceptions, async results and malformed diagnostics fail closed with
`VALIDATOR_FAILURE`. Guards reject reentrant edits to the owning project and to a
draft undergoing validation. This is not a sandbox for malicious extension code:
trusted functions execute in the caller's process and must obey the purity contract.

Hooks run for acceptance, standalone validation, previews, load and undo/redo.
Unmatched types receive generic structural checks only; acceptance does not claim
that their implementation is available. F03 must supply that registry constraint.
The public example injects real point-coordinate, label-text/anchor, relationship-
endpoint and fixture-size validators. Tests also inject independently written rules.

Failure objects are `KernelError`s. `VALIDATION_FAILED` includes
`.validation = {valid:false,errors:[{code,path,message}]}`. Other useful codes are
`STALE_TOKEN`, `STALE_HANDLE`, `DUPLICATE_ID`, `REFERENCED_REMOVAL`, `UNKNOWN_ID`,
`FOREIGN_HANDLE`, `CLOSED_DRAFT`, `EMPTY_HISTORY`, and `REENTRANT_MUTATION`.

## Limits and F02–F09 requirements

State and history currently use full in-memory copies without a history-retention
limit. Node/operation workload budgets are not universal in F01; fixtures impose
their own size limits. Large-project indexing, asynchronous validation, schema
migrations, persisted history, executable recipes stored in projects, scientific
calculation, providers, rendering and persistence packaging are not implemented.
The schema is strict about its top-level/node fields; future additions must update
the shared contract intentionally. Project title/identity are supplied at creation
or load; there is no separate project-metadata edit command yet.
